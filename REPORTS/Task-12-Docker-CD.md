In `src/main/resources/application.properties`, the application defined static defaults for local development:   ```properties   spring.datasource.url=jdbc:h2:mem:toilet_db;DB_CLOSE_DELAY=-1   spring.datasource.driverClassName=org.h2.Driver   spring.jpa.database-platform=org.hibernate.dialect.H2Dialect   ```2. In Docker Compose, `SPRING_DATASOURCE_URL` was overridden with `jdbc:postgresql://public-toilet-db:5432/toilet_tracker_db`.3. HikariCP checks whether an explicit `driverClassName` is defined before attempting JDBC URL auto-detection. Because `spring.datasource.driverClassName=org.h2.Driver` was hardcoded, HikariCP instantiated `org.h2.Driver` and passed it the PostgreSQL JDBC URL.4. `org.h2.Driver` threw `java.lang.RuntimeException` because it only accepts `jdbc:h2:` URLs, crashing the Spring `ApplicationContext`.### 5.3 Non-Destructive ResolutionFollowing DevOps best practices for container 12-factor configuration, the packaged source code was kept intact. The driver class and Hibernate dialect were overridden at runtime via Docker Compose container environment variables:```yaml      - SPRING_DATASOURCE_DRIVER_CLASS_NAME=org.postgresql.Driver      - SPRING_JPA_DATABASE_PLATFORM=org.hibernate.dialect.PostgreSQLDialect```Spring Boot's relaxed environment variable binder gave these container variables higher precedence over packaged properties, allowing HikariCP to instantiate `org.postgresql.Driver` and successfully connect to `public-toilet-db`.---## 6. Academic Viva Voce Preparation### Q1: What is the primary purpose of Docker Compose in a microservice or multi-tier application?**Answer:** Docker Compose is a declarative orchestration tool used to define, configure, and manage multi-container Docker applications. Instead of running complex, independent `docker run` commands with extensive flags, Docker Compose uses a YAML file (`docker-compose.yml`) to define services, networks, volumes, environment variables, and dependencies. It enables developers and DevOps engineers to create, start, stop, and destroy an entire multi-tier stack with a single command (`docker compose up -d` / `docker compose down`), ensuring reproducibility across development, testing, staging, and production environments.### Q2: How does Docker Compose resolve dependencies using `condition: service_healthy` versus standard `depends_on`?**Answer:** A standard `depends_on` declaration only controls container startup ordering: Docker starts container B before container A, but container A begins running immediately after container B's process is launched. If container B is a database like PostgreSQL, the database engine takes several seconds to run initialization scripts, allocate shared memory, and bind to port 5432. During this bootstrap window, container A (the application) will attempt to connect and crash. By combining `depends_on` with `condition: service_healthy`, Docker Compose waits until container B's active `healthcheck` command (e.g., `pg_isready`) returns exit code `0` before starting container A, completely eliminating race conditions.### Q3: Why is a named volume preferred over a bind mount for containerized database persistence?**Answer:** Docker named volumes are managed entirely by the Docker daemon within a dedicated storage directory (`/var/lib/docker/volumes/` on Linux/WSL2). They offer several significant advantages over host bind mounts:1. **Host OS Abstraction & Portability:** Named volumes do not depend on host-specific directory structures or Windows-Linux path syntax differences.2. **File System Performance:** On Docker Desktop for Windows (WSL2), accessing host Windows directories (`/c/Users/...`) across the virtualization 9P/virtiofs boundary incurs significant I/O latency. Named volumes live natively inside the WSL2 ext4 virtual disk, providing near-native I/O throughput essential for database ACID transactions.3. **Permissions & Security:** Named volumes maintain native Linux user/group ownership (`postgres:postgres`) without encountering Windows NTFS permission conflicts or file-locking errors.4. **Lifecycle Protection:** Running `docker compose down` deletes containers and networks but automatically preserves named volumes unless the destructive `-v` (`--volumes`) flag is explicitly supplied.### Q4: Explain the difference between `docker compose down` and `docker compose down -v`.**Answer:*** `docker compose down`: Gracefully stops and removes all containers, networks, and internal links created by the Compose project. Named volumes defined in the `volumes:` block are **retained intact**, ensuring database records and state persist for subsequent runs.* `docker compose down -v`: In addition to stopping and removing containers and networks, it **permanently deletes all declared named volumes** and their stored data. This represents a destructive operation that completely wipes database state and cannot be undone without external backups.### Q5: How does DNS service discovery function within a Docker bridge network?**Answer:** When Docker creates a user-defined bridge network (such as `public-toilet-net`), it automatically enables an embedded DNS server at IP address `127.0.0.11`. Whenever a container joins the network, Docker registers its container name and service name as DNS aliases. When `public-toilet-app` attempts to connect to `jdbc:postgresql://public-toilet-db:5432/...`, the container's resolver queries `127.0.0.11`, which resolves `public-toilet-db` to its active internal IP address (e.g., `172.18.0.2`). This decouples services from volatile, dynamic container IP addresses.### Q6: How does Spring Boot's property precedence hierarchy enable runtime container overrides without modifying application code?**Answer:** Spring Boot utilizes a well-defined `PropertySource` hierarchy. Packaged properties located in `src/main/resources/application.properties` occupy position #17 (low precedence). Environment variables injected into the container (via Docker Compose `environment:`) occupy position #10 (high precedence). When `SPRING_DATASOURCE_DRIVER_CLASS_NAME` is defined in Docker Compose, Spring Boot's relaxed property binder automatically overrides the lower-priority `spring.datasource.driverClassName=org.h2.Driver` entry packaged inside the JAR, adhering strictly to 12-factor configuration principles.---## 9.
